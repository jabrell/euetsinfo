# Bundle is not a Pipeline

When formalising the pipeline abstraction in `eutl_scraper/pipeline/`, we considered making a **Bundle** (the source-grouped collection that replaces today's `pipeline_eutl`) a subclass of **Pipeline** with the same `load` / `transform` / `save` phases, on the grounds of self-similarity and a single mental model for "thing the user invokes." We rejected this: a Pipeline owns a real `load`/`transform`/`save` over one cohesive product, whereas a Bundle's only runtime job is `for p in self.pipelines: p.run()` plus a factory step that selects pipelines based on source-level runtime config (API keys, user-supplied paths). Forcing the Pipeline phase names onto the Bundle would have made three of its four methods misnomers — e.g. `Bundle.save` would have contained the cross-entity Augment Pipelines, whose work is transformation, not saving. Instead, Bundle and Pipeline share **only** a `run()` method (Composite pattern). This also matches the Dagster mapping we may pursue later: Pipeline → asset/op, Bundle → job/Definitions are different primitives by design.
